# Лабораторна №2: архітектурні рішення

## Користувачі та ролі
- Таблиця `users`: email (унікальний), хеш пароля, ім'я, роль, ознака активності.
- Ролі `user` та `admin` задані enum (`UserRole`): значення обмежені на рівні
  БД і коду, помилитися в написанні ролі неможливо.
- Реєстрація створює лише роль `user`. Роль у запиті ігнорується, тому
  привілеї підняти через API не можна. Адміністратор створюється
  скриптом `python -m scripts.create_admin`.

## Автентифікація
- Пароль зберігається лише як хеш PBKDF2-HMAC-SHA256 із випадковою сіллю та
  600 000 ітерацій; порівняння через `hmac.compare_digest`. Реалізація на
  стандартній бібліотеці: без нативних залежностей, які на деяких системах
  блокуються політиками безпеки.
- Вхід повертає JWT (`sub` = id користувача, `exp` = час життя). Сервер
  не зберігає сесій, тому бекенд лишається stateless і легко масштабується
  за балансувальником (див. архітектурну схему ЛР №1).
- Відповідь на неправильний логін однакова для «немає користувача» і
  «неправильний пароль», щоб не розкривати, які email зареєстровані.

## Розмежування доступу
- Залежність `get_current_user`: немає або недійсний токен, відповідь 401.
- Залежність `require_admin`: не адміністратор, відповідь 403.
- Захист від IDOR: операції над даними (`PATCH /users/{id}`,
  `POST /bookings/{id}/cancel`) перевіряють, що власник ресурсу збігається
  з поточним користувачем, інакше 403. Адміністратор має виняток.

## Бізнес-логіка (MVP)
- Адміністратор керує локаціями та ресурсами, користувач бронює й скасовує
  власні бронювання.
- Конфлікти часу: при створенні бронювання рядок ресурсу блокується
  (`SELECT ... FOR UPDATE`), потім перевіряється перетин інтервалів.
  Перевірено на PostgreSQL: з 8 одночасних запитів на один слот успішним
  був лише один (201), решта отримали 409.
- Усі дати зберігаються в UTC.
- Бронювання не видаляється, а отримує статус `cancelled`: зберігається
  історія, а слот знову стає вільним.

## Міграції та тести
- Схема БД керується Alembic (`alembic upgrade head`), а не створюється
  вручну або при старті застосунку.
- Тести (pytest) працюють на окремій БД SQLite в пам'яті через підміну
  залежності `get_db`: ізольовані, швидкі й не торкаються робочої БД.
  Покрито: анонімний доступ (401), вхід (200/401), вертикальне
  розмежування (403), горизонтальне розмежування IDOR (403), конфлікти
  бронювань.
